# Backend API

## Purpose

This document describes the API areas and their important interaction semantics. Swagger/OpenAPI, controller code, DTOs, and MVC tests remain authoritative for exact fields, validation constraints, and response schemas.

With the backend running locally:

- Swagger UI: `http://localhost:8080/swagger-ui.html`
- OpenAPI JSON: `http://localhost:8080/v3/api-docs`

## Company Context and Authentication

DISPO, dashboard, resend, and settings endpoints are company-scoped.

- Outside the `prod` profile, the backend uses a fixed company context for company `1`.
- In the `prod` profile, callers provide `X-API-Key`. The backend hashes the value and resolves the matching company.
- A missing or invalid production API key returns `401 Unauthorized` using the standard error envelope.

Customer endpoints do not use the company API-key resolver. They address a confirmation request through its opaque customer token.

## DISPO Confirmation Requests

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/dispo/confirmation-requests` | Accept current order, delivery-window, contact, channel, and deadline data from DISPO. |

The endpoint persists the current request state and starts or updates asynchronous work. It does not wait for e-mail/SMS/WhatsApp delivery.

The response body contains `externalOrderId` and the current order `confirmationStatus`.

- `202 Accepted` is returned when the resulting status is `OPEN` and delivery work is pending or being reconciled.
- `200 OK` is returned when the use case reuses an existing non-`OPEN` result.

A successful `202` therefore means that the backend accepted the work, not that the customer message has already been delivered. Provider delivery failures happen in the Camunda workflow and are represented in persisted request/dashboard state; they are not a synchronous `502` result from this create call.

Validation and company/contact resolution still happen synchronously. Invalid DTO data or delivery windows return `400`, a missing channel-specific contact returns `422`, and an unknown company returns `404`.

See [Confirmation Workflow](confirmation-workflow.md) for lifecycle and replacement behavior.

## Customer Confirmation

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/customer/confirmations/{token}` | Load the customer-facing delivery preview and current confirmation status. |
| `POST` | `/api/customer/confirmations/{token}/response` | Submit `CONFIRM` or `REJECT` with an optional customer comment. |

The customer link generated by notification adapters is:

```text
{frontend-url}/confirmation/{token}
```

The frontend extracts the token, loads the preview, and submits a response only while the request is active and unexpired. A successful response returns `204 No Content`.

Expected conflict cases include an inactive request, an expired request, or an existing response. Exact codes and messages are defined in `GlobalExceptionHandler` and tested by the customer MVC/integration tests.

## Customer Tracking

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/customer/confirmations/{token}/tracking-info` | Report whether tracking is available and, when resolved, the delivery target coordinate. |
| `GET` | `/api/customer/confirmations/{token}/driver-location` | Return the latest driver coordinate when available. |

Tracking is available only on the delivery date. The tracking-info response may report availability without a target coordinate if geocoding does not resolve the delivery address. The driver-location endpoint returns `404` when no current coordinate is available.

Both responses use `Cache-Control: no-store`.

## Dispatcher Dashboard

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/dispo/dashboard/tours` | Load paged, filtered tours and their orders. |
| `GET` | `/api/dispo/dashboard/tour-numbers` | Load tour-number filter options. |
| `GET` | `/api/dispo/dashboard/orders/{externalOrderId}` | Load the company-scoped order and full confirmation-request history. |
| `POST` | `/api/dispo/dashboard/orders/{externalOrderId}/resend` | Start a new asynchronous confirmation request for an existing order. |

The resend endpoint returns `202 Accepted` with the order in `OPEN` state. It does not wait for notification delivery. See [Dashboard](dashboard.md) for filters, grouping, detail status mapping, and resend restrictions.

## E-mail Settings

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/dispo/settings/email` | Read the current company's SMTP settings without exposing the stored password. |
| `PUT` | `/api/dispo/settings/email` | Create or update the current company's SMTP settings. |
| `POST` | `/api/dispo/settings/email/test-connection` | Test the configured SMTP connection. |
| `POST` | `/api/dispo/settings/email/test-message` | Send a test message to the configured sender address. |

The response indicates whether a password is configured but never returns the password. An omitted password on update preserves the existing encrypted password when authentication remains enabled. Disabling authentication removes stored username/password values.

See [Configuration](configuration.md#company-specific-settings) for storage and encryption responsibilities.

## Error Envelope

Handled API errors use a consistent JSON object with these fields:

| Field | Meaning |
| --- | --- |
| `code` | Stable machine-readable error category. |
| `message` | Human-readable explanation. |
| `status` | HTTP status code as an integer. |
| `path` | Request path that failed. |
| `timestamp` | Failure time as an instant. |

Do not maintain a copied list of every error code here. `GlobalExceptionHandler`, exception types, and controller tests are the current source of truth. Clients should branch on the HTTP status and documented machine-readable `code`, not on the message text.
